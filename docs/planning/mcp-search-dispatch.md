# MCP search + dispatch redesign

**Status:** Planning (2026-06-06)  
**Authority:** Complements [MCP_DEBUGGING_TOOLS.md](../technical/MCP_DEBUGGING_TOOLS.md), [AGENTS.md](../../AGENTS.md), [DIAGNOSTICS.md](../DIAGNOSTICS.md). Does **not** replace [API_CONTRACT.md](../technical/API_CONTRACT.md) or [openapi.yaml](../reference/api/openapi.yaml).

## Executive summary

Today the backend exposes **~54 FastMCP tools** (one per operation) plus **3 router meta-tools** (`be_find`, `be_domains`, `be_card`) on a separate stdio server. Domain-split profiles (`is-be-diag`, `is-be-jobs`, …) reduce bloat per connection but agents still face a large, unstable surface and a two-step “find server → call tool” flow.

**Target:** A compact, stable MCP surface on the backend:

| Tool | Role |
|------|------|
| **`search`** | Lexical discovery over a structured **action registry**; never executes side effects |
| **`dispatch`** | Execute one action by `action_id` with schema validation, policy, dry-run, confirmation, audit |

Legacy per-operation MCP tools remain during migration (Phase 5), then deprecate.

## 2. Proposed MCP tool schemas

### 2.1 `search`

```python
def search(
    query: str,
    *,
    limit: int = 10,
    category: str | None = None,           # diagnostics | data | jobs | maintenance | logs | ...
    side_effect_level: str | None = None,  # read_only | writes_db | ...
    read_only_only: bool = False,
    pipeline_area: str | None = None,      # phase_code or user-facing stage label
    include_schemas: bool = False,
    include_docs: bool = False,
) -> dict: ...
```

**Behavior:**

- Search **action registry** only (not live DB/API).
- Reuse `Bm25Index` with extended fields: `aliases`, `intent_examples`, `argument_names`, `canonical_docs` snippets.
- Apply filters before ranking.
- Set `low_confidence: true` when top score &lt; threshold (e.g. 0.35) or gap between rank-1 and rank-2 is small.
- Include `matched_fields` and normalized `confidence` (0–1).
- Optional `dispatch_hint` with suggested `action_id` + partial `args` parsed from query (best-effort, no execution).

**Result shape:** As specified in task brief (see §2.1 in requirements); stable JSON keys documented in `docs/technical/MCP_SEARCH_DISPATCH.md` after implementation.

### 2.2 `dispatch`

```python
def dispatch(
    action_id: str,
    arguments: dict | None = None,
    *,
    dry_run: bool = False,
    confirmed: bool = False,
    request_id: str | None = None,
    allow_deprecated: bool = False,
) -> dict: ...
```

**Behavior:**

1. Resolve `action_id` in registry; 404-style structured error if unknown.
2. Reject `deprecated` unless `allow_deprecated=True`.
3. Validate `arguments` against action `input_schema` (JSON Schema draft 2020-12 subset).
4. Evaluate policy: confirmation, profile, env flags (`ENABLE_MCP_EXECUTE_CODE`, etc.).
5. If `dry_run` and action supports it → return planned effects without mutating.
6. Invoke `canonical_backend_handler` (see §5).
7. Return normalized envelope: `status`, `summary`, `data`, `warnings`, `errors`, `artifacts`, `logs_ref`, `request_id`, `canonical_docs`.

**Errors:** Structured MCP errors (`code`, `message`, `action_id`, `request_id`, `retryable`, `policy`); map Python exceptions via `modules/mcp/errors.py`.

## 3. Action registry schema

### 3.1 Storage layout

```
mcp/
  action_registry.schema.json    # JSON Schema for registry entries
  actions/
    overlay.yaml                 # Curated metadata, intent examples, policy overrides
  action_registry.json           # Generated: overlay + introspection + OpenAPI refs
```

**Generation:** Extend `scripts/generate_mcp_tool_inventory.py` with `--update-action-registry` / `--check-action-registry` (mirrors catalog CI).

### 3.2 Action record (required fields)

```yaml
action_id: diagnostics.get_error_summary   # stable dotted id
title: Error summary overview
description: Failed jobs, missing scores, orphans, stale running phases
category: diagnostics
tags: [errors, triage, health]
aliases: [error summary, failure overview]
intent_examples:
  - why did scoring fail
  - system error overview
input_schema:                          # JSON Schema object
  type: object
  properties: {}
  additionalProperties: false
output_schema:                         # optional summary schema for dispatch envelope.data
side_effect_level: read_only           # enum per requirements
confirmation_required: false
dry_run_supported: false
auth_or_policy_requirements:
  - requires_db
canonical_backend_handler:
  kind: python_function
  module: modules.mcp_server
  function: get_error_summary
canonical_docs:
  - docs/DIAGNOSTICS.md
  - docs/technical/MCP_DEBUGGING_TOOLS.md
api_contract_refs: []                  # empty when not REST-backed
version: 1
deprecated: false
replacement_action_id: null
test_refs:
  - tests/test_mcp_search_dispatch.py::test_dispatch_get_error_summary
```

### 3.3 Handler kinds (`canonical_backend_handler.kind`)

| Kind | Use when | Example |
|------|----------|---------|
| `python_function` | Existing MCP impl in `mcp_server.py` | `get_failed_images` |
| `python_callable` | Other modules | `modules.doctor_cli.run_doctor` |
| `fastapi_operation` | Thin HTTP wrapper | `GET /api/health` → `health_check_api_health_get` |
| `script_cli` | Subprocess with fixed argv | Not in v1 unless needed |
| `unsupported` | Placeholder for future | `pipeline.rebuild_embeddings` until implemented |

**Rule:** Registry documents the handler; OpenAPI remains canonical for REST. MCP actions must not invent request/response fields not in API contract.

## 5. Safety and confirmation policy

### 5.1 Defaults by `side_effect_level`

| Level | `search` | `dispatch` without `confirmed` | `dry_run` |
|-------|----------|----------------------------------|-----------|
| `read_only` | Allowed | Allowed | N/A (no-op or schema-only) |
| `writes_db` | Allowed | **Rejected** | Required first when supported |
| `writes_files` | Allowed | **Rejected** | Required first when supported |
| `starts_job` | Allowed | **Rejected** | Return planned job manifest |
| `destructive` | Allowed with banner in result | **Rejected** | Mandatory dry_run when supported |

### 5.2 Additional gates

- **`execute_code`:** Requires `ENABLE_MCP_EXECUTE_CODE=1` and SSE/WebUI context (unchanged).
- **`execute_sql`:** Enforce existing SELECT-only guard; reject multi-statement.
- **`export_debug_bundle`:** Never auto-upload; response includes review reminder per [DIAGNOSTICS.md](../DIAGNOSTICS.md).
- **Secrets:** Handlers must use `_sanitize_for_mcp` / redaction helpers; never return `secrets.json` contents.
- **Audit:** Log `{request_id, action_id, dry_run, confirmed, actor, duration_ms, status}` to structured logger (and optional `debug.log` event).

### 5.3 Profile interaction

- New profile **`compact`**: only `search` + `dispatch` registered on `is-be-router` (or rename to `is-be-mcp`).
- Domain profiles (`diagnostics`, `jobs`, …) unchanged during migration; `dispatch` checks action category against allowed profile set when `MCP_TOOL_PROFILE` ≠ `full`/`compact`.

## Appendix A — Proposed code modules

```python
# modules/mcp/actions/dispatch.py (sketch)
def dispatch_action(
    action_id: str,
    arguments: dict | None,
    *,
    dry_run: bool = False,
    confirmed: bool = False,
    request_id: str | None = None,
    allow_deprecated: bool = False,
    profile: str | None = None,
) -> dict:
    record = registry.require(action_id)
    policy.check(record, dry_run=dry_run, confirmed=confirmed, profile=profile)
    validated = schema.validate_arguments(record.input_schema, arguments or {})
    if dry_run and record.dry_run_supported:
        return envelope.planned(record, validated, request_id)
    if policy.needs_confirmation(record) and not confirmed:
        raise PolicyError("confirmation_required", record)
    result = handlers.invoke(record, validated)
    audit.log_dispatch(record, request_id, status="success")
    return envelope.success(record, result, request_id)
```
